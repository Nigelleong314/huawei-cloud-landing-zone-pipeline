# Contributing

## Dev setup

Either an editable install:

```bash
pip install -e .
```

or nothing at all — the root `conftest.py` puts `pipeline/` and `app/` on `sys.path` for pytest, and every entry point runs directly from the checkout (`python pipeline/lz_pipeline/lzctl.py`, `python -m lz_pipeline` from inside `pipeline/`).

Dependencies: Python ≥ 3.10, `openpyxl`, and Terraform ≥ 1.6.3 on PATH if you touch HCL (the harness's `fmt`/`validate` checks skip without it).

## Before every PR

```bash
pytest
python -m lz_spec.verify_pipeline
```

Both must pass. The harness's `regen-diff` check is the determinism contract: if your change alters generated bytes, that is a deliberate event — recapture goldens (below), never hand-edit generated files.

## Schema changes ripple

`pipeline/lz_spec/schema.py` is the authoritative schema definition; changing it obligates you to regenerate every derived artifact:

```bash
# 1. Questionnaire — the coverage check FAILS the build if any non-exempt
#    schema table is unreachable from every question, so wire new tables
#    into the question catalogue first
python -m lz_pipeline.tools.gen_questionnaire -o questionnaire.xlsx --check

# 2. JSON Schema
python -m lz_pipeline.tools.gen_jsonschema -o schemas/lz.spec.schema.json

# 3. Blank workbook template (template-check fails while it is stale)
python -m lz_spec.gen_template pipeline/lz_spec/landing_zone_spec.xlsx

# 4. Goldens, if generated output changed
python pipeline/lz_pipeline/tests/make_goldens.py

# 5. Prove it all
python -m lz_spec.verify_pipeline
```

If a new field reaches Terraform, also wire it through `pipeline/lz_pipeline/core/builders.py` (see "Adding a new field" in `pipeline/lz_spec/README.md`).

## Comment hygiene

Shipped HCL and Python stay concise: comments explain the non-obvious *why*, in one or two lines. Engagement lore, war stories, and long rationale go in the docs (or the relevant skill asset), not in code the customer inherits. The handover rule applies to comments too — a customer operator reads the tree without our context.

## Fixture sanitization

Never commit customer-derived values — names, CIDR prefixes, domains, email domains, on-prem identifiers — to fixtures, example specs, schema samples, or docs. The **leak-guard test is the enforcement** (`pipeline/lz_pipeline/tests/test_phase5.py`): it derives forbidden tokens from every non-example export profile's spec and scans the example specs and exported artifacts, so a leaked identifier fails CI rather than shipping. When you need realistic data, invent it (the synthetic `example` customer in `pipeline/lz_pipeline/fixtures/` is the pattern). Do not weaken the guard to make a fixture pass; fix the fixture.
